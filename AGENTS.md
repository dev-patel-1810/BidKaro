## Product context
BidPilot AI is an AI-assisted tender discovery, eligibility, and compliance workflow. The planned MVP proves one official tender source end to end: discover/fetch with TinyFish, collect documents, extract source-cited requirements, compare them against a company profile and evidence library, then produce a fit report and compliance checklist.

## Non-negotiable domain rules
- Every requirement shown to a user needs source document, page (viewer and printed page if they differ), clause/form reference when available, verbatim excerpt, and source URL plus retrieval time. If it cannot be verified, mark it Unverified / partial / conflicting; never fabricate citations, requirements, authorities, deadlines, or consequences.
- Keep mandatory eligibility (`Pass` / `Fail` / `Unknown`) separate from the soft fit score. Unknown or missing evidence is never a pass, and a high score must not hide a failed mandatory criterion.
- Checklist items must be tender-specific: exact document/action, acceptance criteria, issuer/signatory, evidence checks, deadline or trigger, and consequence only when the source states it. No generic filler such as "check legal requirements".
- Do not assume standard requirements (notarization, stamp paper, affidavit, licence, validity period); extract each from the actual tender.
- TinyFish is the required web discovery/extraction integration and should do real work on a real source. Manual PDF upload is only a fallback for blocked sources.
- Never solve a captcha, an OTP or a login on the user's behalf. Detect the challenge, screenshot it, and let the user answer; the agent then continues in the same session. The live preview iframe is read-only, so it can show the browser but never act for the user.
- Use deterministic code for scoring, date normalization, deduplication, schema validation, and citation checks. Treat model output as untrusted until validated.
- The product supports decisions; it must not claim legal eligibility or submit bids autonomously.

## Implemented shape
Main orchestrator plus Discovery (TinyFish), Extraction, Analysis, Compliance, and Monitoring components, backed by deterministic validation and persistence. Persist tenders, documents, requirements, evidence matches, checklist tasks, and change snapshots with provenance. Built as a modular monolith (`routes -> services -> repositories -> MongoDB`) with company-scoped queries.

- Discovery: `app/integrations/tinyfish.py` (REST `GET /v1/search`, `POST /v1/fetch`, header `X-API-Key`), `services/discovery_service.py` (query building, prequalify, batched fetch, store, qualify), `services/tender_extraction.py` (deterministic fields, source type, dedupe, listing detection, listing-table rows), `services/relevance.py` (profile fit with reasons), `repositories/discovery.py`, routes under `/api/discovery` (`status`, `run`, `runs`, `sources`, `tenders`, `tenders/{id}`, `save`, `dismiss`).
- Checkpointed Run Discovery: `services/discovery_run.py` runs the search pipeline in batches of `DISCOVERY_BATCH_SIZE` (5), writes a checkpoint after every batch, then runs the two existing agent workflows in order (autonomous, then interactive) through `AgentScraperService` - it calls them, it never changes them. `DISCOVERY_SEARCH_ENABLED` is off by default, which skips the search stage entirely so a run starts with the autonomous workflow; turn it on to run search first. `POST /api/discovery/runs/start` returns at once and `GET /api/discovery/runs/{id}` is polled for progress; `POST /api/discovery/runs/{id}/cancel` stops the run and its agent workflows. The synchronous `POST /api/discovery/run` is unchanged. One run per company at a time; a run whose worker died resumes from its checkpoint. The interactive workflow's challenge is surfaced on Discover and answered through the existing `POST /api/agent/runs/{id}/challenge`; the autonomous one cannot be answered and is reported as stopped. The agent walks keep their own notice budgets, but the run hands each workflow the room it has left, so `DISCOVERY_MAX_TENDERS` is a ceiling on tenders listed, not on notices parsed: the candidate pool is widened to cover it, and a workflow is skipped once the ceiling is reached. `DISCOVERY_RESET_LIST_ON_RUN` is off by default and leaves the whole stored list visible; when on, a run shows only the tenders it touched itself, so older ones leave the view without being dismissed or saved and come back only if a later run finds them again.
- Tender documents and OCR: `services/pdf_extraction.py` (PyMuPDF text, viewer page index, printed label, bounded OCR fallback, `no_text_layer`), `services/ocr.py` (English Tesseract via `pytesseract`/`Pillow`, page render, timeout and failure reporting), `services/download.py` (public-host/size/magic-byte checks, redirect re-validation), `services/requirement_service.py` (upload dedupe by SHA-256, page persistence, chunking, per-item Pydantic validation, citation checks, review), `repositories/tender_documents.py`, routes in `api/routes/tender_documents.py`.
- AI: `integrations/ai.py` exposes a provider interface with Groq (`openai/gpt-oss-120b` default, JSON mode, bounded retries on 429/5xx) and Gemini. Output is untrusted; each item is validated individually so one bad item cannot sink a chunk.

A match found only in OCR text is stored `needs_review`, not `verified`. Otherwise it is stored `unverified` with a reason. `needs_review` and `rejected` are human states and are audited. Re-running extraction skips duplicates; `replace=true` deletes AI-origin requirements for that document first.

Only individual, still-open tenders are listed: a deadline or reference must be extracted, index/award pages are excluded, and past deadlines are dropped. Portal/index pages are stored, shown separately (`GET /api/discovery/sources`) and never listed as tenders. Dated tables on listing pages are parsed into individual tenders (`extracted_from: listing_table`). Social hosts are blocked before scoring. Relevance is profile fit only, never eligibility. Date-only deadlines are anchored at noon UTC so the calendar day survives IST display.
- Agentic scraping: `app/integrations/tinyfish_agent.py` (Agent API `run-async`/`runs`/`cancel`, Browser API `sessions` with session id, CDP URL and base URL), `app/integrations/browser_driver.py` (Playwright over CDP; never calls `browser.close()`, which would kill the remote session), `services/agent_scraper.py` (goal, output schema, challenge detection, deterministic field verification, human handoff), `repositories/agent_runs.py`, `models/agent.py`, routes in `api/routes/agent.py` (`status`, `runs`, `runs/{id}`, `runs/{id}/challenge`, `runs/{id}/cancel`, `runs/{id}/captures/{file}`, `runs/{id}/notices/{notice_id}/save`, `runs/{id}/notices/{notice_id}/documents`).
- Agent rules: the goal is fixed so the same fields come back every time; the agent is told to report `human_required` instead of trying to pass a captcha; a challenge stops the run, is screenshotted, and the user types the answer, after which the agent continues in the same session; the page is never reloaded while it waits; every field is re-derived from the page text with `tender_extraction`, and an agent value the page does not state is kept on the card and marked `unverified` rather than dropped — the Discover card shows the same Authority/Reference/Deadline/Value/Location as the agent browser, and the saved record carries `discovery_extracted.unverified` so nothing unproven reads as a citation; the residential proxy exits from India by default; the live preview is read-only.
- Agent saving and documents rules: every notice a run read is stored as a tender, so it carries a `discovered_tender_id` and the agent page can save it (`POST /api/agent/runs/{run_id}/notices/{notice_id}/save`) exactly as the Discover page's Save button does; a notice that was never stored as a tender has nothing to save and says so; a single-notice run stores its one notice the same way. The walk reads the document links off the notice page (`_DOCUMENT_LINKS_JS` in `services/portal_walk.py`) and they are shown in full on the agent page and the Discover card, so the user can copy an address out. `POST /api/agent/runs/{run_id}/notices/{notice_id}/documents` pulls the files into the saved tender's Documents section: the file is fetched by the same browser session that opened the notice (`download_in_page` in `app/integrations/browser_driver.py`), because the portal ties it to that session; a zip is opened and its PDFs attached one by one, and a file that is not a PDF is reported, never attached; the bundle is fetched first and the first link that hands over documents wins; the autonomous mode has no browser session, so it says so instead of pretending.
- Document-fetch captcha rules: a portal may answer a file request with a captcha page instead of the file. The Central Public Procurement Portal answers with a form post (`id="frmCaptcha"`, action `/eprocure/app`) that carries its own hidden fields - `formids`, `seedids`, `component=frmCaptcha`, `page=DocDownCaptcha`, `service=direct`, `session`, `tokenSecret`, `If_17` - an answer input `name="captchaText"` and the picture of the challenge drawn inline as `img#captchaImage` with a `data:image/png;base64,...` source. That page is recognised by `parse_captcha_form`, and **both** the answer input and the picture must be there: a page that merely mentions a captcha is not a captcha, and the portal's every page mentions it in its markup. The page a file request answers with is opened and read as a page, not judged from the `fetch()` bytes alone: the portal can draw the captcha on the navigated page while the fetched HTML is a wrapper, so the link is opened the way a person opens it and `parse_captcha_form` plus the DOM detector read the resulting page. The picture shown to the user is the challenge itself, decoded from the page, beside a full screenshot of the page for context, because a person cannot answer what they cannot see. The user types the answer in the app; `POST /api/jobs/{id}/challenge/answer` carries it into the portal's own form once (fill plus the portal's Submit), then drops it. The answer is never written to Postgres, a log line, a metric or a file, and it is never echoed back. A rejected answer keeps the same file request pending and shows the portal's new picture (bounded retries per link); a portal that never accepts one is reported instead of looped on. An accepted answer's response page is read for its own file or download link, and the original captcha URL is never requested again: that request is what draws a new captcha, so a page that hands over nothing marks the link done with a clear error instead of looping. One fetch shows at most six pictures in total, then reports the rest rather than asking forever. Cancel is cooperative: the job heartbeat checks the row, a cancelled job raises `JobCancelled`, the walk or fetch stops at its next step, and the browser session is closed; a parked job is closed at once. The form's seed and token never travel to the browser. The software never solves the challenge. The window stays minimized because there is nothing to open; the Documents panel shows the captcha picture, the full screenshot, the answer box and a note that the answer is used once and not saved, and it reloads the documents when the job finishes. A document link is tried in order pdf -> file -> unknown -> zip, and the bundle is the fallback only when no individual file arrived, so a portal that hands each PDF over does not cost a second captcha for a zip of the same files. A manually uploaded zip is accepted too: each PDF inside it is attached as its own document and a non-PDF member is reported, never attached.
- Browser session rules (rebuild, `app/discovery/sessions.py`): a browser session is a **thread**, not an object in a dictionary. Playwright's sync API belongs to the thread that created it, so the whole job body - walk or fetch - runs on one daemon owner thread (`SessionLane`) and the worker thread only waits for the result; a resume after `needs_you` reaches that same thread even when a different worker claims the job. Without this, greenlet raises "Cannot switch to a different thread" inside `download_in_page`, which used to be swallowed as a per-link file error and lost the captcha the human had just answered. The lane lives as long as the session, including while parked, and `close`/`close_all` route the driver close through it (inline when already on the owner thread) with a bounded wait so a stuck page cannot hang shutdown. A resumed job whose session is gone (process restart) starts again from the beginning and says so. A closed window is `partial` with one clear human note, the challenge closed and **no automatic retry**: any closed-target error is translated to `SessionLost` at the lane boundary, and a driver that swallowed one still sets `lost`, so `_finish` and the handler report the same note instead of a per-file error. An answered challenge restarts the attempt budget (`attempts = 0`) because a handoff is progress, not a retry; the budget is for errors. A parked session is not running the page's event loop, so a resume pumps it (`wait_for_download`) before reading the download queue - reading first would miss the file the answer produced and ask for a new captcha. The window is **minimized while the software works** (`begin_work` sets `Browser.setWindowBounds` to `minimized` over CDP, falling back to a 480x360 window when there is no window to minimize) and the page is covered by a CSS `backdrop-filter` blur plus a moving sheen, so a person who restores it mid-walk sees the loading state, not the portal. Only `reveal` restores it, uncovers it, expands it to 1280x920 and raises it for the human; `open` raises the window only in human mode, so a walk never steals the screen. A fetch challenge never calls `reveal`: the captcha is answered in the app, so the window stays minimized and the screenshot is taken while minimized (verified not blank). The cover is a pair of pseudo-elements (a style tag), never a DOM node, so it does not enter `inner_text` and cannot pollute extraction or challenge detection, and `pointer-events: none` keeps the automation's own clicks working; an init script re-applies it on every navigation. A minimized window still accepts clicks, typing and navigation (verified), so the walk keeps reading while it sits in the taskbar. The challenge panel must say what to do, not just offer a button: it shows the captcha picture, the full page screenshot, an answer box and a short note that the answer is carried into the portal once and never saved. A rejected answer refreshes the picture (bounded retries), because telling a first-time user nothing is how the same captcha gets answered blind.

- Portal walk rules (`services/portal_walk.py`): the walk is code, not an agent goal, because a portal is a fixed sequence of pages. The organisation is chosen by word-boundary matching against the profile ("broadcast" must not match "road"), and a road-specific name outranks a generic public works department, whose list mixes roads with hospitals, courts and electrical work; a profile term that is itself only a generic public-works word (`PWD`) does not promote a generic organisation. The region breaks the order within a tier, it does not filter the tenders, and it never lifts a generic body above a road-specific one. One organisation cannot take the whole notice budget, so the department reached first cannot hide every later one, and the run records what each organisation contributed and why it stopped. The tender list is filtered by work type and a closing date in the future, and the row test is the listing gate's own rule (`relevance.work_type_match`, with the organisation chain as region context) rather than a looser approximation of it, so the walk never spends a notice on a row the gate would discard. The title is the first bracketed group of the list cell; the reference number in the second group is never read as prose, and the walk returns to the list after each notice so the next row is still reachable. A notice cannot be opened by its own address: the portal binds it to the session that opened it, so the whole walk happens in one browser session and the stored `notice_url` carries a session token. The stable identifier is the tender id. A list can link to the old `/nicgep/` application, which the portal answers with "Not Found", so the walk opens the same application at `/eprocure/`; a page that is still an error page is counted as unread, never stored as a tender, so a dead link cannot produce a card with no authority, reference or value. The portal's search form carries a captcha on the directory and list pages, but that form captcha does not block a page whose organisation table or tender list is already readable: the walk reads the content first and reports a challenge only when there is no content to read, so the search form cannot stop a run that could have listed tenders. A real blocking challenge parks the walk instead of ending it: the browser session stays alive, the challenge picture and the full page are screenshotted, and the job waits in `needs_you`; the human reads the picture in the app and types the answer there, the software carries it into the portal's form once, and the walk restarts from the directory in the same session. A second challenge is reported rather than looped on, and an unattended headless run reports the block instead of parking because nobody is there to answer it.
- Run reporting rules: a run says what it did, not just whether it succeeded. A notice the agent read without a link is kept on the record and shown as read-but-unlinked, and is never stored as a tender because an unopenable notice cannot be cited; when nothing is listed the run states whether it read nothing, read notices with no link, or read notices that failed the listing rules. Portal runs carry the walk counts (rows seen, notices read, notices without link, notices unreadable because the page answered with an error, listed, per organisation) so a run that read and discarded never looks like a run that found nothing.
- Agent execution: the browser work runs on a daemon thread pool, so a walk that takes minutes never holds up the request that started it and never keeps the process alive at shutdown. A challenge is answered by the user through `POST /api/agent/runs/{id}/challenge`, which records the answer; the waiting agent picks it up, types it in and walks again.
- Agent knobs: `TINYFISH_AGENT_BASE_URL`, `TINYFISH_BROWSER_BASE_URL`, `AGENT_MAX_STEPS` (0), `AGENT_MAX_DURATION_SECONDS` (0), `AGENT_MAX_WAIT_SECONDS` (120), `AGENT_POLL_INTERVAL_SECONDS` (2), `AGENT_BROWSER_TIMEOUT_SECONDS` (900), `AGENT_BROWSER_PAGE_TIMEOUT_MS` (90000), `AGENT_PROXY_COUNTRY_CODE` (IN), `AGENT_WALK_MAX_PAGES` (5), `AGENT_WALK_MAX_NOTICES` (10), `AGENT_WALK_MAX_NOTICES_PER_ORG` (4, 0 means no per-organisation limit), `AGENT_WALK_MAX_ORG_PAGES` (8), `AGENT_WALK_MAX_ATTEMPTS` (3), `AGENT_CHALLENGE_WAIT_SECONDS` (600). A step or duration limit of 0 means the limit is not sent at all, because not every TinyFish account is enabled for custom limits and the request is refused with 403. Playwright is optional and only needed for the interactive mode.
- Discovery matching rules (Phase 5 rework): a tender is listed when (a) it names one piece of work, (b) the work matches the company's services, sectors or keywords, (c) a closing date was read and it is still in the future, and (d) the notice is an Indian one. The region only decides the order, never the visibility. Profile terms are matched as plain text with deterministic variants (plural form, "B of A" word order) and every match is explained in `relevance.reasons`. A bare keyword hit needs a region match as well, so an ambiguous acronym such as "AMC" cannot list a tender on its own.
- Discovery reading rules: a closing date is read from a labelled closing/submission word, and a date labelled publish/open is never used as the closing date. Unlabelled table rows use the latest date in the row, except a CPPP-style row (S.No, e-Publish, Closing, Opening, title cell, organisation chain), which takes the **middle** date as the closing because the last one is the opening date; reading it as the closing would tell the user they have days they do not have. Headerless tables are read positionally. A portal's list cell holds the work, the reference and the tender id together (`[Name] [Ref][2026_NHAI_295179_1]`), so they are split there: the first bracketed group is the title, the group matching the portal id shape is the tender id, the other identifier is the reference, and the first organisation-chain segment is the authority; nothing is invented when a group is missing. A work description that names a state or a date is still the title, because only a short cell can be date/value/location metadata. A heading table reads the tender id and the place from its own columns. The verbatim row is the evidence for every field the row states. A search result that describes one work becomes a tender even when the page it points at is a category page (`extracted_from: search_result`). Pages that name an authority but no work are not tenders. Sources are typed as `official_portal`, `authority` or `aggregator`, and every candidate is counted with the reason it was not listed.
- Discover/agent parity rules: Discover and the agent browser read the same notice with the same extractor, so the same link shows the same authority, organisation chain, reference, tender id, closing date, published date, value and location in both places; a field the page does not state reads "Not stated in source" in both, and nothing is filled from the agent's word alone. A notice page (`is_notice_page`) is read as one tender and its own fee/cover/document tables are never tenders. A field ends where the next field's label begins, so a one-line summary or a flattened row (`NHAI HQ Pincode 110075`) does not swallow the following field. A zero or "NA" value is no value. A page the portal answers with an error ("Not Found") is read by neither side and is never stored. One tender is one record, keyed by the portal tender id (`tender_identity_key`), so a list row, a fetched notice and a browser read merge; the fuller read fills the other's gaps (`_carry_forward`) and a second read never empties a field the first read had.
- Assessment rules: score is 25% profile fit + 20% citation verification + 40% confirmed mandatory evidence coverage + 15% tender document readiness. Eligibility is separate; `pass` needs a verified **or human-confirmed `accepted_ocr`** citation plus human-confirmed non-expired evidence, `fail` needs a confirmed contradiction, otherwise `unknown`. Evidence suggestions never auto-pass. Checklist generation selects mandatory/submission/compliance/form-referenced requirements, is idempotent and preserves human status/owner; it copies the citation at generation.
- Workflow rules: `services/workflow.py` captures snapshots of normalized tender fields plus requirement fingerprints (no PDF copies); the content hash covers both, human review status is excluded from diffs, and a failed TinyFish recheck reports the error without fabricating a change. Snapshot capture times are strictly increasing per tender (`_after`, stepped by a whole millisecond) and the snapshot sort has an id tie-breaker, because the system clock is coarse enough for two snapshots in the same tick to share a time and "the latest snapshot" would then be an older one. `services/reminders.py` derives reminders from deadlines and dated tasks, reopens them when the due date changes, and never sends email without explicit opt-in and `SMTP_APP_PASSWORD`. `services/calendar.py` emits authenticated, tenant-scoped ICS only (no Google Calendar OAuth). `api/routes/workflow.py` exposes changes, snapshots, refresh, reminders and both ICS downloads. `scripts/send-reminders.py` is the cron-able email job (dry-run by default, exit 2 without SMTP). Post-award obligations are cited performance/contract requirements; pre-award tasks and post-award obligations stay separate, and old tasks without `phase` are treated as `pre_award`.

## Rebuild in `backend_v2/` (in progress)
A from-scratch rebuild is in `backend_v2/`. Stages A-F, I, J and K are done; the docs are the contract:
- `docs/SYSTEM-BLUEPRINT.md` — the design of record: rules, data model, jobs, locators, corrigenda lineage, the rebuild inventory and the traps that must not be repeated.
- `docs/CODING-GUIDE.md` — how to write the code: layers, transactions, naming, recipes, testing, and what not to do.
- `docs/SCHEMA-SPEC.md` — column-level Postgres schema, enum catalogue, constraints, and the Stage A migration checklist.
- `docs/API-SURFACE.md` — the HTTP contract: endpoints, payload rules, status codes.
- `docs/README.md` — the index and read order.

`docs/archive/DISCUSSION-TRANSCRIPT.md` is **history, not spec**: it contains decisions that were later reversed. Never use it as a source of truth.

In `backend_v2/`: storage is Postgres (Alembic migrations, ephemeral-Postgres tests), MongoDB is absent, and TinyFish is removed entirely. Qdrant and the document question-answering feature are **deferred**, so no vector store is needed initially. Scraping is a separate module (`app/discovery/`) behind the interfaces in blueprint Part 17; it registers its routes and `scrape_portal` handler at startup, and the base installs and tests without Playwright because the browser is imported lazily. `FEATURES_DISCOVERY=false` hides the module's routes/handler. Where this file still describes Mongo, TinyFish or `backend/`, it describes the **old oracle**, not the rebuild.

Key rebuild decisions that override the old tree:
- The corpus is global; per-company relevance is computed at read time, never used as a storage filter. `GET /api/tenders` returns a `relevance` object (`score`, `matched_terms`, `reasons`, `region_match`) per item. `GET /api/checklist` returns the company's tasks across tenders, filtered by `phase`/`status`.
- The tender list is server-side: `sort` (`created_desc` default, `created_asc`, `closing_asc`, `closing_desc`, null deadlines last, unknown is a 422), `q` (contains search over title, reference, authority, organisation chain, location, portal id; `%`/`_` literal), `mine` (saved or bidding only), `limit`/`offset`. The response is `{items, total, page, pages, next, profile_complete}`; `total` counts every visible row, so a page and its count are honest even though the profile gate runs in Python. `profile_complete=false` means the company declared no services, sectors or keywords (a region alone is not a work profile): the list is then the whole corpus, shown under an "all tenders" heading with a prompt to finish the profile. Discover and My tenders both page 10 at a time from this one contract.
- Register/request-code return a generic `202`; user/company are created only on code verification. The JWT claim never authorises; tenancy is reloaded from Postgres. There are no roles.
- Global `PATCH /api/requirements/{id}` may set only `needs_review`, `rejected` or `accepted_ocr`, never `verified`; a `rejected` row stays visible to all. `PATCH /api/company/documents/{id}` handles metadata; company documents are soft-deleted.
- Captcha is never solved by the software; a human supplies the answer. `POST /api/jobs/{id}/challenge/answer` carries that answer into the portal's own form once and drops it: no answer column, log line, metric or echo exists. `POST /api/jobs/{id}/challenge` remains the signal-only path for a human who acted outside the app. A `needs_you` job holds a bounded `lane_leases` reservation, not a worker thread.
- Requirements are never hard-deleted (`is_active`); `replace=true` deactivates AI rows. `assessment_criteria` aggregates any Fail -> Fail, else any Unknown -> Unknown.
- Evidence points at `company_document_version_id` with `RESTRICT`; expiry/soft delete recomputes and clears confirmation.
- Assessment is deterministic and recomputed on read: the gate uses only `mandatory_state='mandatory' AND category='eligibility'`; confirmed evidence must be current; `rejected`, navigation and company-ignored requirements are excluded. The soft score is 25 profile fit + 20 citation verification + 40 confirmed mandatory evidence + 15 document readiness. `accepted_ocr` can pass only when a human accepted the OCR citation, and the response keeps `ocr_confirmed=true`. Checklist generation is idempotent and copies the citation.
- Workflow is deterministic: snapshots are global corpus history with strictly increasing capture times and an id tie-break, content hashes cover tender fields plus requirement fingerprints (never review state), and changes are the factual diff between two snapshots. Change review is an audited global annotation. Reminders are company-scoped, re-derive from deadlines and task due dates, and reopen when a due date moves. Calendar export is authenticated ICS only. A corrigendum link is proposed only when portal, normalised reference, organisation, work title and a later publication date all match; a human confirms it, and a shared reference alone never links two tenders.
- Discovery (Stage I) is deterministic: `app/discovery/portal_walk.py` walks the CPPP directory and list in one browser session, filters rows with the same work-type rule the read-time gate applies, and records every URL it saw as a `discovery_candidates` row with `kind`/`outcome`/`reason` (a rejection is a row, not a count). Organisation ranking uses only the profile's own words (a multi-word phrase outranks a single word, then the company's regions, then the directory's own order); there is no built-in list of authorities or work vocabulary and no name is excluded, so a body whose name says nothing is still walked once the stronger matches have had their turn. The browser is a local Playwright adapter imported lazily; tests use a fake page. Ingestion upserts one global tender by `(portal_id, portal_tender_id)`, falling back to the no-date `dedupe_key`, and a later read fills gaps but never empties a field the first read had. `tender_locators` stores the stable portal id, not the session-bound notice address. `discovery_candidates` source rows power `/api/discovery/sources`. `GET /api/tenders` applies per-company relevance at read time, hides dismissed rows by default, and keeps saved/bidding rows visible even when the profile changes. A tender whose portal page explicitly states the current bidding cycle is terminated (the portal's own sentence) gets `tenders.cycle_state='terminated'` with `termination_excerpt` and `termination_observed_at`; a walk skips such a notice rather than storing it, and a recheck records it and returns the fixed message. A missing notice, a vanished row or a passed deadline never sets it. The card and the detail page show only the terminated-cycle message, with no authority, reference, value, deadline, documents or tabs (`0004_tender_cycle`).
- Corpus-first discovery: `app/discovery/sweep.py::PortalSweeper` reads only the directory and listing pages into the global corpus (`POST /api/discovery/sweeps`), breadth-first across organisations, staleness-ordered rather than by a positional cursor, committing one list page at a time so a cancel at the next page boundary keeps every page already read. It needs no profile and opens no notice: notice depth stays lazy (run discovery, or the pre-warm for saved/bidding/matched tenders). There is no per-organisation cap; `sweep_max_organisations`/`sweep_max_pages_per_org` (0 = uncapped) exist only as a runaway ceiling. A sweep never parks for a human: a challenge is reported, the sweep stops and keeps what it stored, because a midnight `needs_you` would hold the browser lane all night. Only a fully `done` sweep resets the nightly clock. The scheduler enqueues `sweep_portal` when its handler is registered and falls back to `scrape_portal` otherwise.
- Read-time fit is an ordered ladder and never eligibility (`app/discovery/relevance.py`): 1 = a confirmed capability/experience match **and** a support term, 2 = a confirmed match alone, 3 = two support units and the company's region, 4 = two support units, 5 = one support unit and the region, 6 = one support unit, 7 = nothing or the AI could not tell. A whole phrase counts two units, a single term or partial token one. Tiers 1-3 are `strong`, 4-6 `possible`, 7 `hidden` (excluded unless `include_hidden=true`, then returned with its bucket). The score is only a band inside the rung (90-95, 80-88, 70-78, 60-68, 50-58, 40-48, 0-25) and is capped at 95, so the UI never reads 100%. The work text is reduced by `app/discovery/work_text.py`: places, buyer/department words, organisation acronyms and boilerplate (`computer`, `document`, `software`, `entry`, `high`, `technical`) are not evidence, while a buyer word that is also work ("data centre", "college building", "court records") survives inside the phrase. Matching is phrase/word-order aware ("data processing" = "processing of data") and expands common acronyms (DMS, AMC, CCTV ...). Rarity from `TenderRepository.recent_titles()` is data-derived and only explains a reason; it never promotes a rung. "Not relevant" (`POST /api/tenders/{id}/not-relevant`) is negative feedback with `DEMOTE_PENALTY = 0.15` per rejected term: it demotes to at least tier 4 (clamped at 6 if the score would be lower), never bans, and repeats of the same term do not stack. Closed tenders are hidden by default (`closing_at < now`); an undated tender is unknown, not closed, and stays visible, while `mine=true`/`saved=true`/`bidding=true` retain a closed row and `include_closed=true` is the explicit escape hatch. The lists default to `sort=match_desc` (fit descending, then newest first) because fit is a read-time verdict, not a column, so the ordering is applied in Python over the gate's own result; the four SQL orders stay selectable. The saved list has two distinct actions: `DELETE /api/tenders/{id}/save` removes only the bookmark and its `relevant` feedback row (the tender is not dismissed and can be saved again; a bid in preparation keeps the row and the response says `bidding: true`), while `not-relevant` removes it from both lists and records the negative weight. `TenderOut.saved`/`.bidding` come from the company's own row so a card never guesses.
- Verdicts and audit: `company_tender_verdicts` caches a per-company answer keyed by `verdict_input_hash(profile_hash, tender_content_hash, feedback_hash, rules_version)`, so a profile edit, a save, a "not relevant", a re-published notice or a new rules version all cause recomputation while a plain repeat read does not. `tender_content_hash` lives in `app/repositories/intelligence.py` and is used by **both** the read path and the background pass, because two different hashes made every read a cache miss. Evidence is deliberately not part of the key (work-type relevance only); deadlines and dismissals stay live filters. `tender_observations` is append-only evidence of every sighting. `classification.py` labels a title from its own significant words (grammar-only stoplist) once, stamped with `rules_version` + content hash; `adjudication.py` asks the AI only about the ambiguous residue (rules bucket `possible`, `source == "rules"`), id-in/id-out, defaulting to `unknown`/shown on any error, and it can only decide "is this the company's work". An anchored `yes` stores tier 1 when the rules already matched a support term and tier 2 otherwise; a `no` stores tier 6 (possible, demoted), never hidden. The AI pass is bounded by `classification_batch_size` (50) and `classification_max_batches` (20) per invocation; `POST /api/discovery/classify` queues it on demand and a finished sweep queues it automatically.
- Company-document intelligence: an uploaded `about_company` PDF is read by a durable `extract_company_document` job through the same PyMuPDF + bounded English OCR reader as tender documents (`app/services/company_intel.py`). The harvest keeps repeated multi-word phrases (2-4 words) plus the specific words inside them; each term carries its page and verbatim line. Client/empanelment segments, contact lines and CIN/PAN/GST identifiers are stripped before counting, so a client or authority name is never work evidence, and a boilerplate-only stoplist (never a work vocabulary) removes words that describe any company or tender. Terms are human-facing suggestions: they never feed fit, never override the declared profile and never touch eligibility. Only a human-confirmed capability/experience or a declared profile term may match. `company_document_pages` and `company_document_terms` are derived data (`0007_company_document_intel`); a soft-deleted or reclassified document's terms stop counting at read time. `POST /api/company/documents/{id}/extract` re-reads (optionally after OCR), `GET .../terms` shows page/excerpt, and `DELETE .../terms/{term_id}` removes one. The understanding signature (not the raw terms) is part of the verdict profile hash, so a confirmation, edit or removal recomputes. The Documents tab recommends the profile, shows extraction state, and opens a terms panel; `RULES_VERSION` is `2026-11-20.1`.
- Company understanding and work comparison: an `about_company` profile is also read for **capabilities** (kinds of work) and **experiences** (named projects/products), each with the 1-based page, printed label, verbatim line, OCR flag and a `proposed`/`confirmed`/`rejected` state (`app/services/company_understanding.py`, `app/repositories/understanding.py`, `0008_company_understanding`). Every quote is validated against the page with `normalize_for_match` before storage, a company-name line is never a capability, and a human must confirm before anything is used; proposed and rejected rows stay visible but unused. `GET /api/company/understanding` returns the documents, items and counts; `PATCH /api/company/capabilities/{id}` and `PATCH /api/company/experiences/{id}` confirm, reject or edit (an edit sets `origin=human`). The work comparison is a **closed label** only (`app/services/similarity.py`): `yes`/`no`/`unsure` on "is this the same family of work", id-in/id-out, batched and bounded, with no score, free-form reasoning, eligibility call or invented capability. A `yes` counts only when its quoted anchor is found in the notice's own work text; an unanchored `yes` is stored `unsure` with `needs_confirmation` and shown as "AI suggested — confirm". `no` sets the verdict to tier 6 (possible, demoted) and appends a reason, never hides; an anchored `yes` sets tier 1 when the rules already matched a support term and tier 2 otherwise; the adjustment is applied at read time on top of the rules verdict, so `company_tender_verdicts` stays rules-only and eligibility never changes. The prompt holds 16 cross-sector few-shot examples (civil, goods, equipment, services, digitisation and the negatives). Judgments are cached in `tender_similarity_judgments` by `(tender_content_hash, confirmed capability signature, rules_version)` and keep model/prompt provenance. `GET/POST /api/tenders/{id}/similarity` judge one tender; `POST /api/discovery/similarity` enqueues the bounded `judge_tender_similarity` job over the visible page (`{job, created}`, no duplicate stacking). Requirement coverage (`app/services/requirement_experience.py`) maps requirements to confirmed capabilities/experiences as `covered`/`partial`/`new`/`unknown`, cites both sides from stored rows (never model output), stores `unknown` for a skipped requirement rather than `new`, and reuses a mapping by input hash; `GET/POST /api/tenders/{id}/requirement-experience` serves it. A generated checklist task for a `new` requirement says "New work: …" in its evidence check. Settings: `similarity_batch_size` (8), `similarity_max_tenders` (40), `requirement_match_max_requirements` (40). Versions `UNDERSTANDING_VERSION` and `MATCH_VERSION` are `2026-11-18.1`; `SIMILARITY_VERSION` is `2026-11-20.1`.
- `GET /api/tenders` page contract is unchanged by the gate: `total` counts every row the request would return, so with `include_hidden=true` the page and the count widen together and still agree.
- Startup schema guard: `app/core/schema.py` compares the database's `alembic_version` stamp (read once, never assumed) with the migration head this checkout carries; the head is read from `migrations/versions/*.py` with `ast` (revision minus every `down_revision`), so the server never imports alembic and boots in an install that carries only the app requirements. A database stamped behind head stops startup with a `RuntimeError` naming both revisions and the `alembic upgrade head` command, because a stale schema otherwise fails one request at a time with `UndefinedTable` and reads as a code bug. An unstamped database is reported as `revision: null`, an unreadable or branched migration directory only warns, and an unreachable database still boots so `/api/health` can report it down. `/api/health` returns `schema: {revision, head, up_to_date}` and is `degraded` when the schema is behind or the database is down. `SCHEMA_CHECK=false` boots a stale database deliberately (warns instead of raising) and is not a deployment mode.

## Open decisions

The old Phases 2-6 in `backend/` are implemented; the rebuild has completed Stages A-F, I, J and K plus the company-intel and understanding slices, and the frontend is adapted to it.
